# AI 学习原则

## 背景

用户是一名软件开发工程师，正在学习 AI 和新技术。长期目标是成为 AI 开发工程师，同时提升工程能力，并保持持续学习，不追短期热点。

## 长期目标

- AI 开发工程师方向
- 提升工程能力
- 持续学习，而不是追热点

## 学习优先级

### 第一层：重点学习

- Python 最小开发能力
- 大模型 API
- Prompt 与结构化输出
- Tool Calling
- AI Agent
- RAG
- MCP
- 项目实战

### 第二层：工程基础支撑

- FastAPI
- 数据库
- Linux
- 网络基础
- Docker
- Git、CI、日志、测试、部署

这些内容要加入学习框架，但按项目需要逐步补齐，不替代 AI 开发主线。

## 工程基础处理规则

不要把工程基础当成进入 Agent 前必须整块学完的前置课程。原则是：

- 先用最小关卡证明当前任务真正需要的 Python、环境、异常、文件/JSON 和 HTTP 能力。
- 已有正式 PASS 的基础不机械重学，只在新项目中迁移；暴露缺口时再做窄范围补强。
- Linux、网络、数据库、Docker 放进 Agent/API/RAG 项目里随用随补。
- 每次只补当前任务需要的最小工程知识。
- 只有当项目需要本地多服务、数据库持久化、Docker Compose、Memory/RAG 或部署时，再做完整工程基础整合关卡。

## 前后端与开源骨架偏好

- 后续 Agent 项目的后端统一使用 Python/FastAPI，不同时维护第二套后端实现。
- 用户会一些 Vue，但自述本身不替代证据；进入真实界面任务时先用最小切片确认已经掌握的部分，不机械重上整套入门。
- 助手可以在任务实际启动时，从 GitHub 查找并组合开源 Vue 骨架，但必须先检查许可证、维护状态、依赖和安全风险；不提前囤积未来项目。
- 助手负责机械搭建不等于用户掌握。用户仍需审核关键改动，并能解释或修改组件状态、SSE、认证、错误处理、数据流与密钥边界。
- 多个后端项目只选一个作为正式产品旗舰，避免重复建设两套前端、公网部署和产品级观测。

### 第三层：保持关注

- OpenAI 更新
- Anthropic 更新
- Gemini 更新
- MCP 生态更新

### 第四层：暂不深入

- 刚发布的新框架
- 新 Agent 产品
- 新模型
- 短期热点

除非工作需要、项目需要或社区大量采用，否则只记录，不深入学习。

## 节奏原则

- 连续性比时长重要。
- 以知识单元和 Session 接力；跨日不清零，W 只是稳定内容块编号，不是日历周。
- 单次时间短也可以，但必须保留明确的已覆盖、未覆盖和下一起点。
- 身体累就休息。
- 不追求每天学习很多。
- 避免因为压力过大而放弃学习。
- 课程 PASS、算法债务和岗位证据分别记账，不能互相冒充。

## 新技术处理规则

当 AI 出现新技术时，先判断：

1. 它是什么。
2. 是否值得关注。
3. 是否应该进入学习队列。

不要默认把新技术加入学习计划。

## 回答偏好

后续学习规划、复盘、知识库整理和技术更新判断，都应优先遵守这套学习原则。

## 从概念到动手的带学方式

- 默认从零解释；在职经历或自述不代替掌握证据。已经正式通过或当场独立证明的内容只承接新增部分，不换措辞反复考察。
- 助手先给出可修改的具体工作场景、资料与最小成功例，讲清“输入 → 处理 → 可见结果”，再解释当前知识点。用户已经委托规划时，不继续要求凭空创造角色和需求。
- 新概念先说它是什么、解决什么问题、怎样接到前后步骤，并用比喻或图示说明；例如进入 RAG 项目前先理解资料准备和查询生成，不能先堆框架字段。
- 边读边练：讲清一个有意义的目标后做一道只覆盖该目标的考察。通过证据累计到同一任务，正式练习补缺口；跨日不重置题量。
- 用户负责尚未证明的理解、判断、实现与解释；助手自动整理设计、必要格式和 notes，完整验收前由用户审核。助手完成的方案、代码或演示须标明来源，不计用户独立证据。
- 未教完的任务保持学习中；中途检查只记录已学范围与下次起点。代码骨架在当前动手检查点需要时才创建，测试保留最小但充分的可复用内容。
- 规则与维护范围以当前 Codex 项目记忆和三个学习 skill 的源文件为准，不主动维护 Claude 侧副本。

## Agent 模拟面试流程

用户会在学习会话中使用“开始今天的模拟面试”启动一次面试。面试官应以 `AI-Agent-Learning` 当前已通过的学习任务为主要题库：覆盖新近内容、间隔复测较早内容，并提高此前薄弱点的出现频率；未正式学习的内容不能作为扣分项。

每题流程固定为：用户作答后，先给出 `通过 / 部分通过 / 需要复测` 的结论；指出答对点和关键缺口；再给出一版更完整、适合面试表达的参考回答；最后进入下一题。题目可包含少量综合场景，检验概念组合与工程取舍。

每次面试结束后，应将题目、用户回答要点、结论、不足、纠正建议与下次复测重点写入当日的项目学习记录，供后续面试追踪。重点关注 Agent、Tool Calling、结构化输出、控制循环、可靠性、安全边界与已学习内容对应的工程验证。
